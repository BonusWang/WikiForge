## 二、逐项评审

### 2.1 路径扫描安全

#### 2.1.1 已有约束（值得肯定）

| 约束 | 出处 |
|------|------|
| 文件扫描路径必须由用户显式配置 | 技术架构 §6.7.1、§8；MVP 实施计划 §8 |
| `WIKIFORGE_ALLOWED_SCAN_ROOTS` 环境变量控制允许扫描的根路径 | 技术架构 §6.7.1 |
| 不扫描系统盘根目录 | MVP 实施计划 §8 |
| 不扫描隐藏目录（除非用户显式开启） | MVP 实施计划 §8 |
| 要求校验路径在允许目录内，避免路径穿越 | 技术架构 §6.7.1 |

#### 2.1.2 P0 阻塞问题

**P0-1：路径穿越防护缺乏具体实现规范**

文档中多处提到"防止路径穿越"、"校验路径在允许目录内"，但未给出任何具体的校验方法。路径穿越可以通过以下方式绕过简单的前缀匹配：

- 符号链接（symlink / junction）：用户可将 `/allowed/path/link` 指向 `/etc/` 或 `C:\Windows\`
- 目录连接点（Windows junction）：`mklink /J` 创建的目录连接
- `..` 遍历：`/allowed/path/../../../etc/passwd`
- 大小写混淆（Windows）：`C:\ALLOWED\..\windows` 与 `C:\allowed\..\Windows`
- UNC 路径：`\\?\C:\allowed\..\windows` 绕过常规路径解析
- 8.3 短文件名（Windows）：`C:\ALLOWE~1\..\WINDOWS`

**建议：必须明确路径校验流程——在扫描入口对每个文件路径执行 `Path.toRealPath()`（Java NIO）规范化后，再与 `WIKIFORGE_ALLOWED_SCAN_ROOTS`（同样规范化后的白名单）做前缀匹配。符号链接目标路径也需要校验。**

**P0-2：符号链接处理策略完全缺失**

所有文档均未提及如何处理符号链接。在本地文件系统扫描场景中，符号链接是一个关键安全边界：

- 如果用户在白名单目录内放置了指向外部的符号链接，扫描是否会跟随？
- 如果跟随，目标路径是否需要同样受白名单约束？
- 递归目录扫描时，符号链接可能导致无限循环（`/a/link -> /b/link -> /a/link`）

**建议：MVP 应明确符号链接策略——推荐默认不跟随符号链接，或在跟随后对目标路径同样执行白名单校验。同时需要设置递归深度上限，防止循环符号链接导致无限遍历。**

#### 2.1.3 P1 高风险问题

**P1-1：扫描深度无上限**

文档未定义递归扫描的最大深度。如果用户配置的白名单根目录下存在极深嵌套（如 `node_modules` 深处的依赖树），可能导致：
- 扫描任务超时
- 内存/文件句柄耗尽
- 生成大量无意义的导入记录

**建议：MVP 设置默认最大扫描深度（如 20 层），用户可在高级设置中调整。**

**P1-2："隐藏目录"定义不明确**

技术架构写"不扫描隐藏目录，除非用户显式开启"，但未定义什么是"隐藏目录"：
- Unix/Linux：以 `.` 开头的目录
- Windows：具有 `FILE_ATTRIBUTE_HIDDEN` 属性的目录
- macOS：以 `.` 开头或具有隐藏标记的目录

如果只实现 Unix 语义（`.` 前缀），在 Windows 上 `AppData`、`ProgramData` 等系统隐藏目录将不被跳过。反之亦然。

**建议：MVP 需要同时检查 `Files.isHidden()`（跨平台）和目录名以 `.` 开头两种条件。**

### 2.2 白名单目录安全

#### 2.2.1 已有约束

| 约束 | 出处 |
|------|------|
| `WIKIFORGE_ALLOWED_SCAN_ROOTS` 允许配置多个根路径 | 技术架构 §6.7.1 |
| `path_scan_roots` 存储于 `system_settings` | 数据模型 §25 |
| 不扫描系统盘根目录 | MVP 实施计划 §8 |

#### 2.2.2 P0 阻塞问题

**P0-3：白名单校验算法未定义**

文档只说了"需要校验"，没有说明怎么校验。白名单校验的质量直接决定整个文件系统的安全边界。一个不严谨的实现可能：

- 只用字符串 `startsWith()` → 可以被 `..` 绕过
- 不规范化路径 → 可以被 `/allowed/../` 绕过
- 不做大小写归一化（Windows）→ 可以被 `C:\ALLOWED` vs `c:\allowed` 绕过

**建议：在编码规范中明确白名单校验算法：**
1. **对输入路径调用 `Path.toRealPath()` 获取规范化绝对路径**
2. **对白名单中每个根路径同样 `toRealPath()`**
3. **使用 `Path.startsWith()` 做前缀匹配**
4. **所有比较使用 `toRealPath()` 的结果，不直接使用原始字符串**

#### 2.2.3 P1 高风险问题

**P1-3：白名单配置缺少输入校验**

`WIKIFORGE_ALLOWED_SCAN_ROOTS` 在 UI 设置页允许用户输入路径，但文档未说明前端/后端对路径输入做了哪些校验：

- 是否拒绝空路径？
- 是否拒绝相对路径？
- 是否拒绝非目录路径（如指向文件）？
- 是否校验路径存在且可读？

**建议：在 Settings API 的 `test-path` 端点中，对用户输入的每个允许路径执行：存在性检查、目录类型检查、可读性检查。如果路径不存在或无权限，拒绝保存并给出明确提示。**

**P1-4：白名单运行时变更无防护**

如果用户在系统运行期间修改了 `WIKIFORGE_ALLOWED_SCAN_ROOTS`，正在执行的扫描任务的路径白名单是否需要重新校验？文档未涉及。

**建议：MVP 可以先设计为：路径配置变更后，仅对新创建的扫描任务生效；已运行的任务使用创建时的白名单快照。在代码层面，ScanTask 创建时保存一份白名单副本。**

### 2.3 文件大小限制

#### 2.3.1 已有约束

| 约束 | 出处 |
|------|------|
| MVP 大文件阈值默认 100 MB | MVP 实施计划 §2.1 |
| 超过阈值仅建索引，不解析正文（`raw_text_saved=false`, `raw_text_policy=skip_large_file`） | MVP 实施计划 §2.1；数据模型 §3 |

#### 2.3.2 P1 高风险问题

**P1-5：缺少绝对上限——超大文件仍会被复制**

100 MB 阈值仅控制"是否解析正文"，文件仍会被完整复制到 `WikiForge_RawSources`。这意味着：

- 用户配置了一个包含 50 GB 虚拟机磁盘镜像的目录，系统仍然会尝试复制
- 复制过程可能耗尽磁盘空间、耗时极长且无法中断
- Docker volume 挂载下的磁盘占用尤其危险

**建议：MVP 需要设置一个绝对大小上限（如 500 MB），超过此上限的文件在扫描阶段直接跳过，记录为 `skipped_size_exceeded`，既不复制也不索引。此上限应可配置。**

**P1-6：缺少磁盘空间预检**

复制文件前不检查目标磁盘剩余空间，可能导致：
- 大量文件复制到一半时磁盘写满
- `import_jobs` 部分成功，状态混乱
- 数据库记录"已复制"但文件不完整

**建议：在 `Raw Source Organizer` 开始复制前，预估总复制量（已去重后），检查目标磁盘剩余空间是否至少为预估量的 1.2 倍。空间不足时拒绝任务启动并提示用户。**

### 2.4 Hash 去重安全

#### 2.4.1 已有约束

| 约束 | 出处 |
|------|------|
| 同 hash 文件只复制一份 | MVP 实施计划 §2.1 |
| 重复文件记录为 `duplicate`，记录 `duplicate_of_file_id` | 数据模型 §4 |
| `content_hash` 字段类型为 `varchar(128)` | 数据模型 §3、§4 |

#### 2.4.2 P1 高风险问题

**P1-7：Hash 算法未指定**

`content_hash` 字段长度 128 字符，推测为 SHA-512（hex 编码 128 字符），但文档未明确指定算法。这可能导致：

- 不同开发者使用不同算法（SHA-256 vs SHA-512 vs MD5）
- 与外部系统对接时 hash 格式不一致
- 去重逻辑依赖的 hash 碰撞概率不同

**建议：明确指定使用 SHA-256（64 hex 字符，安全性足够，比 SHA-512 快），或 SHA-512（128 hex 字符，与当前字段长度匹配）。在代码中定义常量 `HASH_ALGORITHM = "SHA-256"`，所有 hash 计算统一使用。**

**P1-8：大文件 Hash 计算缺少流式处理说明**

对 100 MB 级别文件计算 full-content hash 时，如果使用 `Files.readAllBytes()` 一次性读入内存，会导致 OOM。文档中未提及流式 hash 计算策略。

**建议：使用 `MessageDigest` + `DigestInputStream` 流式计算，内存占用恒定。对大文件增加 hash 计算超时机制。**

#### 2.4.3 P2 优化建议

**P2-1：缺少 hash 碰撞处理**

SHA-256 碰撞概率极低，但从防御性编程角度，应该在"发现相同 hash 但内容不同"时（即实际碰撞或计算错误）有兜底逻辑。当前数据模型中只有 hash 去重，没有 fallback 机制。

**建议：在代码中保留 hash 碰撞检测逻辑——如果 hash 相同但文件大小不同，记录为 `hash_conflict` 并写入日志告警。**

### 2.5 复制策略安全

#### 2.5.1 已有约束

| 约束 | 出处 |
|------|------|
| 默认复制，保留原文件不删除 | PRD §6.1；技术架构 §8 |
| 不移动原文件 | 技术架构 §8 |
| `organize_mode` 支持 copy、move、index_only | 数据模型 §5 |

#### 2.5.2 P0 阻塞问题

**P0-4：`organize_mode = move` 在 MVP 中不应暴露**

数据模型中的 `import_jobs.organize_mode` 包含 `move` 选项。虽然 MVP 实施计划中写明"默认复制，不移动、不删除"，但 `move` 枚举值的存在意味着：

- 代码中需要实现 move 逻辑（否则枚举无意义）
- 一旦实现，UI 或 API 可能意外触发移动操作
- 移动操作的不可逆性远高于复制

根据"MVP 暂缓复杂能力"的原则，`move` 模式属于高风险操作，不应进入 MVP。

**建议：MVP 阶段移除 `organize_mode` 的 `move` 枚举值，或将其标记为 `@Deprecated` 并在 API 层返回 400。只保留 `copy` 和 `index_only` 两种模式。`move` 至少在 V1 且具备完整的操作确认和回滚机制后再开放。**

#### 2.5.3 P1 高风险问题

**P1-9：复制操作缺少原子性保证**

文档未提及文件复制是原子操作。如果复制过程中系统崩溃或磁盘满：

- 目标文件可能不完整（写了部分字节）
- 但数据库记录可能已标记为 `copied`
- 后续去重、解析均基于不完整文件

**建议：文件复制采用"写临时文件 → 校验 → 原子重命名"策略：**
1. **将内容写入 `target_path.tmp`**
2. **写完后计算 hash 并与源文件对比**
3. **校验通过后 `Files.move(tmp, target, ATOMIC_MOVE)`**
4. **校验失败则删除临时文件，记录复制失败**

**P1-10：文件被占用时的处理未定义**

Windows 上文件可能被其他进程锁定（如 Word 正在编辑 .docx），此时 Java NIO 复制会失败。文档未说明如何处理。

**建议：扫描阶段检测文件是否可读（`Files.isReadable()` + 尝试打开 `FileInputStream`），不可读时记录为 `skipped_locked`，并提示用户关闭占用程序后重试。**

**P1-11：文件权限和属性丢失**

复制文件时使用 `Files.copy()` 默认不会保留原始文件的创建时间、修改时间、文件属性等元数据。虽然 MVP 不要求完整保留，但如果用户后续依赖文件时间排序，信息已经丢失。

**建议：MVP 复制时至少保留原始文件的 `lastModifiedTime`，通过 `Files.copy()` + `CopyOption` 参数实现。**

### 2.6 同名冲突处理

#### 2.6.1 已有约束

| 约束 | 出处 |
|------|------|
| 同名不同 hash 文件追加短 hash 后缀 | MVP 实施计划 §2.1 |
| 同 hash 文件不重复复制，记录为 duplicate | MVP 实施计划 §2.1 |

#### 2.6.2 P1 高风险问题

**P1-12："短 hash 后缀"规则不明确**

文档写"同名不同 hash 文件追加短 hash 后缀"，但未定义：

- 短 hash 取几位？4 位 hex？8 位？
- 追加在文件名前还是扩展名后？`file_a1b2.pdf` 还是 `file.pdf.a1b2`？
- 如果追加后仍重名（极端情况但可能）怎么处理？

**建议：明确规则——取 SHA-256 前 8 位 hex，追加在文件名与扩展名之间：`原文件名.{8位hash}.原扩展名`。例如 `report.d3f2a1b8.pdf`。如果仍冲突，追加递增序号：`report.d3f2a1b8.1.pdf`。**

**P1-13：Windows 路径长度限制**

Windows 传统 API 默认限制路径长度为 260 字符（`MAX_PATH`）。归集后的 `WikiForge_RawSources/01_Documents_文档/` 加长文件名可能导致路径超限。

**建议：MVP 实现中，对生成的归集路径做长度检查。如果超过 240 字符（为后续操作保留余量），截断文件名主体部分，保留前缀 + hash + 扩展名。在日志中记录截断情况。**

#### 2.6.3 P2 优化建议

**P2-2：文件名中的特殊字符处理**

用户源文件可能包含各种特殊字符（空格、中文、emoji、换行符、`:`、`*`、`?`、`<`、`>`、`|` 等），这些在跨平台文件系统上有不同兼容性：

- Windows 不允许文件名包含 `\ / : * ? " < > |`
- macOS/Linux 不允许 `/` 和 `\0`
- Obsidian 内部链接对某些特殊字符有转义要求

**建议：在复制时对目标文件名做安全清洗，替换不兼容字符为 `_`。清洗后的文件名记录在 `source_files.managed_path` 中，原始文件名保留在 `file_name` 字段。**

### 2.7 obsidian://open 路径安全

#### 2.7.1 已有约束

| 约束 | 出处 |
|------|------|
| URI 格式：`obsidian://open?vault=<vault_name>&file=<vault_relative_path>` | 技术架构 §3.7.1 |
| `obsidian_notes.obsidian_uri` 存储生成的 URI | 数据模型 §15 |
| 通过 Web UI 一键打开 Obsidian 文件 | PRD §12 |

#### 2.7.2 P0 阻塞问题

**P0-5：obsidian://open URI 生成缺少输入校验**

`obsidian://open` URI 由服务端拼接生成，传给前端渲染为可点击链接。如果 `vault_name` 或 `vault_relative_path` 包含未转义的特殊字符，可能导致：

- **协议注入**：如果 `vault_relative_path` 包含换行符或 `%0d%0a`，可能被解析为多个 URI 或执行不同行为
- **路径穿越**：如果 `vault_relative_path` 未校验是否在 Vault 目录内，用户可能构造 `../../../etc/passwd` 路径
- **参数污染**：如果 `vault_name` 包含 `&` 或 `=`，可能破坏 URI 参数结构

**建议：**
1. **`vault_relative_path` 必须经过路径规范化（`Path.normalize()`），确保不包含 `..` 遍历**
2. **规范化后的路径必须 `startsWith()` Vault 根路径（或仅为相对子路径）**
3. **使用 `URLEncoder.encode()` 对 `vault_name` 和 `file` 参数值进行编码**
4. **`vault_name` 在配置保存时应校验合法字符集（字母、数字、中文、连字符、下划线）**

#### 2.7.3 P1 高风险问题

**P1-14：Obsidian 文件预览路径遍历**

`GET /api/obsidian/notes/{id}/preview` 需要从 Vault 中读取 Markdown 文件并返回内容。如果后端仅根据 `obsidian_notes.vault_path` 或 `absolute_path` 读取文件，且数据库记录被意外篡改（或路径写入时未校验），攻击者可以构造路径读取 Vault 外的任意文件。

**建议：预览接口读取文件前，必须执行路径校验：**
1. **用 `obsidian_notes.id` 查询到 `vault_path`**
2. **拼接 Vault 根路径 + `vault_path`**
3. **规范化后校验结果仍在 Vault 根路径目录内**
4. **校验通过后才读取文件内容**

**P1-15：前端 obsidian:// 链接的 XSS 风险**

`obsidian://open` URI 在 Web UI 中渲染为 `<a href="obsidian://open?...">`。如果 URI 中包含了未转义的双引号或 JavaScript 协议头，存在 XSS 风险。虽然 `obsidian://` 不是 `javascript:` 协议，但防御性编码仍然必要。

**建议：前端渲染 obsidian:// 链接时，必须对 href 值做 HTML 属性转义（Vue 的 `:href` 绑定默认会做，但需确认）。后端 API 返回的 `obsidian_uri` 字段值也应做基本的合法性校验。**

## 三、附加发现

### 3.1 评审材料中未覆盖的安全关注点

#### P2-3：文件解析库安全

未在评审要求中明确提出，但文件解析（PDFBox、POI、commonmark-java）本身是常见的攻击面：

- PDFBox 解析恶意构造的 PDF 可能导致无限循环或 OOM
- POI 解析恶意 .docx（zip bomb）可能导致磁盘耗尽
- Markdown 解析器可能产生 XSS 输出（如果 HTML 标签未过滤）

**建议：MVP 在解析阶段增加资源限制——解析超时（30s）、输出大小上限（1 MB 纯文本），使用 DOMPurify 清洗 Markdown 渲染产物中的 HTML。**

#### P2-4：Docker 挂载下的路径差异

技术架构 §6.7.1 要求"镜像内不写死 Windows 本地路径"。但 Docker volume 挂载后，容器内路径与宿主机路径不同。`obsidian_notes.absolute_path` 和 `sources.local_path` 中存储的"绝对路径"在不同环境下含义不同：

- 本地开发模式：`C:\Users\xxx\WikiForge_Vault\`
- Docker 模式：`/data/wikiforge/obsidian-vault/`

**建议：数据模型中区分 `absolute_path`（运行时环境下的绝对路径）和 `host_path`（宿主机路径），obsidian://open URI 应使用宿主机路径。**

#### P2-5：并发扫描安全

文档未说明多个扫描任务是否可以并发运行。如果两个任务同时扫描有重叠的目录：

- 可能重复复制同一文件（hash 去重的 race condition）
- 数据库唯一约束冲突

**建议：MVP 至少在应用层做并发控制——同一时间只允许一个扫描任务处于 `running` 状态。数据库层面 `content_hash` 加唯一索引兜底。**

## 四、评审结论

### 4.1 总体评价

当前文档对本地文件系统安全的**意识是充分的**——多处提到了路径白名单、防止路径穿越、不移动不删除源文件等原则。但**实现细节严重不足**，存在 5 个 P0 级别的阻塞问题，主要集中在路径校验、符号链接处理、obsidian://open 安全三个方面。

### 4.3 是否可以开工

**结论：有条件通过。**

P0 问题必须在编码前完成设计闭环。具体来说：

1. **P0-1、P0-2、P0-3**（路径校验）：必须在 `FileSystemSecurityService` 或同等模块的设计文档中写清楚校验算法，包括 `toRealPath()` 流程、符号链接策略、白名单匹配算法。
2. **P0-4**（move 模式）：从 MVP 数据模型中移除 `move` 枚举值，或在 API 层明确拒绝。
3. **P0-5**（obsidian URI）：必须在 `ObsidianWriter` 的设计中明确 URI 生成前的路径编码和校验步骤。

P1 问题应在 MVP 0（骨架）或 MVP 1（源文件归集）的编码过程中同步解决，不应延后到 MVP 2 之后。P2 问题记录到技术债务列表。

### 4.4 建议的安全编码 checklist（供 MVP 编码参考）

- [ ] `Path.toRealPath()` 用于所有路径规范化
- [ ] 白名单匹配使用规范化路径 + `Path.startsWith()`
- [ ] 扫描入口统一调用 `FileSystemSecurityService.validatePath(path, allowedRoots)`
- [ ] 默认不跟随符号链接
- [ ] 最大扫描深度默认 20 层
- [ ] 文件绝对大小上限默认 500 MB
- [ ] SHA-256 流式 hash 计算
- [ ] 文件复制使用 tmp + atomic rename
- [ ] 复制前检查目标磁盘剩余空间
- [ ] `obsidian://open` URI 参数做 URLEncode
- [ ] 文件预览路径做二次校验
- [ ] 并发扫描控制（单任务运行）
